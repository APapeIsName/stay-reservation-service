---

요구사항을 분석할 때 반드시 다음 7단계 흐름을 따른다.

### 1️⃣ 요구사항을 그대로 믿지 말고, 문제 상황으로 다시 설명한다

- 요구사항 문장을 정리하는 데서 끝내지 않는다.
- "무엇을 만들까?" 가 아니라 "지금 어떤 문제가 있고, 그걸 왜 해결하려는가?" 로 재해석한다.
- 다음 관점을 분리해서 정리한다:
  - 사용자 관점
  - 비즈니스 관점
  - 시스템 관점

> 예시 (숙박 도메인)
> "예약 실패 시 결제를 취소한다" → "결제 성공/실패와 예약 확정/일자별 재고 차감 상태가 어긋나지 않도록 일관성을 유지하려는 문제"

### 2️⃣ 애매한 요구사항을 숨기지 말고 드러낸다

- 추측하거나 알아서 결정하지 않는다.
- 요구사항에서 결정되지 않은 부분을 명시적으로 나열한다.

**다음 유형의 질문을 반드시 포함한다:**
- 정책 질문 — 기준 시점, 성공/실패 조건, 예외 처리 규칙 (예: 노쇼 환불 정책? 체크인 당일 취소 위약금?)
- 경계 질문 — 어디까지가 한 책임인가, 어디서 분리되는가 (예: 재고 차감 = Reservation 책임 / RoomInventory 책임?)
- 확장 질문 — 나중에 바뀔 가능성이 있는가 (예: 객실 단위 가변 가격, 그룹 예약 등)

### 3️⃣ 요구사항 명확화를 위한 질문을 개발자 답변이 쉬운 형태로 제시한다

- 질문은 우선순위를 가진다 (중요한 것부터).
- 선택지가 있는 경우 옵션 + 영향도를 함께 제시한다.
- 본 프로젝트는 `AskUserQuestion` 도구를 사용해 최대 4개 질문을 한 번에 제시한다.

> 형식 예시:
- 선택지 A: 결제 성공 후 예약 확정 → 재고 점유 시간 동안 재고 부족 위험
- 선택지 B: 예약 시 즉시 재고 차감 + 결제 실패 시 보상 트랜잭션 → 구조 복잡, 일관성 보장 명확

### 4️⃣ 합의된 내용을 바탕으로 개념 모델부터 잡는다

- 바로 코드나 기술 얘기로 들어가지 않는다.
- 먼저 다음을 정의한다:
  - 액터 (사용자, 외부 시스템: PG / SMS / 메일 등)
  - 핵심 도메인 (예: Property, RoomType, Reservation, DailyRoomInventory)
  - 보조/외부 시스템

### 5️⃣ 다이어그램은 항상 "이유 → 다이어그램 → 해석" 순서로 제시한다

**다이어그램 작성 전에 반드시 다음을 설명한다:**
- 왜 이 다이어그램이 필요한지
- 이 다이어그램으로 무엇을 검증하려는지

**다이어그램은 Mermaid 문법으로 작성한다.** 사용 기준:

| 다이어그램 | 검증 대상 |
|---|---|
| **시퀀스** | 책임 분리, 호출 순서, 트랜잭션 경계 |
| **클래스** | 도메인 책임, 의존 방향, 응집도 |
| **ERD** | 영속성 구조, 관계의 주인, 정규화 여부 |

### 6️⃣ 다이어그램을 던지고 끝내지 말고 읽는 법을 짚어준다

- "이 구조에서 특히 봐야 할 포인트" 를 2\~3줄로 설명한다.
- 설계 의도가 드러나도록 해석을 붙인다.

### 7️⃣ 설계의 잠재 리스크를 반드시 언급한다

- 현재 설계가 가질 수 있는 위험을 숨기지 않는다:
  - 트랜잭션 비대화 (예약 + 재고 차감 + 외부 결제 호출)
  - 더블부킹 가능성 (동시성)
  - 정책 변경 시 영향 범위 (취소·위약금 등)
- 해결책은 정답처럼 말하지 않고 선택지로 제시한다.

## 톤 & 스타일 가이드

- 강의처럼 설명하지 말고 **설계 리뷰 톤** 을 유지한다.
- 정답이라고 제시하기보다, 다른 선택지가 있다면 함께 제공한다.
- 코드보다 **의도, 책임, 경계** 를 더 중요하게 다룬다.
- 구현 전에 생각해야 할 것을 끌어내는 데 집중한다.

## 프로젝트 통합 — `.claude/rules` 와의 연동

본 Skill 은 이 프로젝트의 rule 들과 함께 동작한다. 호출 시 다음을 자연 적용한다:

### 진행 흐름 체크리스트
- ✅ 분석 결과는 `docs/design/` 에 단일 폴더 누적으로 기록 (라운드별 분리 안 함, 점차 증강)
- ✅ 사용자에게 묻는 질문은 `AskUserQuestion` 도구로 최대 4건 묶음 — [rule 15 process-conventions](../../rules/15-process-conventions.md)
- ✅ 사용자 답변 후 의사결정·트레이드오프는 `docs/round-N/03-questions.md` 에 Q 로 누적 (질의자/제안자 표기)
- ✅ 사용자가 새 컨벤션을 정의하면 [rule 16 user-convention-priority](../../rules/16-user-convention-priority.md) 절차로 즉시 반영
- ✅ 모든 결정은 `의도 + 대안 + 트레이드오프` 가 명시된다 — [rule 04 interview-oriented-output](../../rules/04-interview-oriented-output.md)

### 출력물 매핑 — `docs/design/`

| 파일 | 내용 | 본 Skill 의 단계 |
|---|---|---|
| `01-requirements.md` | 유저 시나리오 + 기능 정의 + 요구사항 명세 + 정책 결정 | 1️⃣ \~ 3️⃣ |
| `02-sequence-diagrams.md` | 최소 2개의 Mermaid 시퀀스 (책임·트랜잭션 경계) | 5️⃣ \~ 6️⃣ (시퀀스) |
| `03-class-diagram.md` | 도메인 객체 클래스 다이어그램 (책임·의존 방향) | 5️⃣ \~ 6️⃣ (클래스) |
| `04-erd.md` | 테이블 구조·관계·인덱스·복합키 (영속성 구조) | 5️⃣ \~ 6️⃣ (ERD) |
| `00-overview.md` (선택) | 도메인 지도 + 라운드별 증강 이력 | 4️⃣ (개념 모델) |

### 완료 체크리스트
- ✅ 사용자 관점·비즈니스 관점·시스템 관점이 각각 1문단 이상 정리됐다
- ✅ 결정되지 않은 부분이 *질문 목록* 으로 명시됐다 (감추지 않음)
- ✅ 사용자 답변 후 결정 사항이 `questions.md` 에 누적됐다
- ✅ 최소 1개의 시퀀스 다이어그램 + 클래스 다이어그램 + ERD 가 Mermaid 로 작성됐다
- ✅ 각 다이어그램 앞뒤로 *이유·해석* 이 붙어 있다
- ✅ 잠재 리스크 (동시성·일관성·트랜잭션 비대화 등) 가 *선택지* 형태로 정리됐다

## 호출 예시

```
> /requirements-analysis 를 통해 아래 요구사항을 분석합니다.
  목표 : 숙박 예약 기능 구현
  요구사항
  - 사용자는 도시/체크인/체크아웃/인원수로 숙소를 검색한다
  - 검색 결과에는 해당 기간의 합산 가격과 1박 평균 가격을 함께 표시한다
  - 사용자는 객실 타입을 선택해 예약을 생성한다
  - 예약 시 일자별 재고가 차감되고, 더블부킹은 발생하면 안 된다
  제안사항
  - 일자별 재고는 (room_type_id, date) 단위 적재
  - 예약 상태는 PENDING → CONFIRMED → CHECKED_IN/CHECKED_OUT → CANCELLED 흐름
```

호출 후 본 Skill 이 7단계 흐름을 따라 진행한다. 시나리오 자료가 있으면 자동 참조한다 (`docs/curriculum/round-N-scenario.md` 등).
